# Cloud dashboard and inbound sync while Docker is off

The owner asked whether the online Super Admin dashboard could remain available while Docker is stopped, with online business records eventually reaching the local master database.

The cloud Super Admin route can use cloud Supabase through the hosted frontend and a valid cloud Super Admin session. When Docker hosts the local app and Supabase, the localhost dashboard and local import require those services to run. The cloud dashboard can show cloud-side data and the local records already uploaded there. Opening the dashboard currently calls expiry and reorder refresh functions, so the existing cloud dashboard is not strictly read-only. [Super Admin route](../../../src/routes/AppRoutes.jsx#L374) · [Supabase client](../../../src/lib/supabase.js#L3) · [Local Docker setup](../../../docker/docker-compose.yml) · [Dashboard service](../../../src/services/dashboardService.js#L25)

The current availability migration rejects new customer QR orders after the local heartbeat is older than 45 seconds. The worktree’s proposed KDS import reads only Pending, Preparing, and Ready orders with their lines. This is insufficient for reliable catch-up across an outage because rows can reach other statuses before local reconnects. The current deployment was not inspected. [Availability migration](../../../supabase/migrations/20261103000000_online_ordering_availability.sql) · [Worker](../../../sync/worker.mjs#L40)

An approach compatible with the local master is to persist approved online business changes and inbound events in cloud, show those and already-synced data in the cloud dashboard, and let the local worker consume events after it restarts. Apply each event and record its acknowledgement transactionally, so a retry cannot duplicate an order or stock movement. Pull from a durable event stream rather than the current order status. Keep ownership and conflict rules explicit for entities that can be edited on both sides. Keeping QR intake open while the kitchen is offline would also need an explicit service policy, such as accepting orders for later processing. This is a proposal only.
