# Why a cloud menu edit stays in cloud

The owner reported that a cloud item edit did not appear locally after the one-time import. Menu edits write to `menu_items` through the Supabase client configured for that frontend. The local sync queue captures local changes and sends eligible batches to the cloud receiver. The checked worktree's inbound KDS path fetches active orders and writes only `orders` and `order_items`. Its live deployment was not verified. [Menu edit service](../../../src/services/inventoryService.js#L138) · [Configured Supabase client](../../../src/lib/supabase.js#L3) · [Outbound engine](../../../sync/engine.mjs#L61) · [Inbound KDS worker](../../../sync/worker.mjs#L40)

The cloud-to-local SQL import established parity at the time of the export. Later menu changes in cloud stay there unless they are reconciled explicitly. For ongoing local-first operation, make new menu and inventory edits in the local app and use the outbound sync. An existing independent cloud edit may conflict if the local version is sent later, so check the specific item before trying to overwrite it.
