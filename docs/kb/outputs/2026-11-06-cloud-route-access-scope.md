# Restricting the hosted DaYo app to dashboard and QR access

The owner asked whether the hosted app could expose only the Super Admin dashboard and customer QR flow while blocking other profiles from staff pages. This is feasible with an explicit cloud route allowlist and cloud database permissions. Keep sign-in available for authorized cloud `SUPER_ADMIN` profiles, expose the customer routes required by the intended QR flow, and keep other staff workflows on the local deployment. If customers only browse, the menu and QR entry suffice. If they order, cart, checkout, and order status also need routes. [App routes](../../../src/routes/AppRoutes.jsx) · [Deployment flag](../../../src/config/deployment.js)

In the current checkout the dashboard route already requires `SUPER_ADMIN`, but the shared router still defines other staff pages and Vercel uses an SPA fallback. Some database policies and staff RPCs allow ordinary `ADMIN` access. An enforced cloud restriction needs both the route allowlist and cloud-side policies or RPC grants, with checks for direct URLs and API requests. The local staff permissions can remain separate. [Route guard](../../../src/components/auth/ProtectedRoute.jsx) · [Role allowlists](../../../src/constants/userRoles.js) · [Vercel routing](../../../vercel.json) · [Current staff policies](../../../supabase/migrations/20261020143115_remote_schema.sql#L1477)

The existing customer gate uses a QR session for the app flow, and checkout validates the token. Menu data itself is readable through the public `get_customer_menu` RPC, and the current session creation RPC is callable anonymously. If the requirement is actual QR-only access to menu data, change the database to validate a QR-specific credential before issuing a session or returning menu data. This assessment describes the worktree and a proposal. Live routes and permissions were not tested.
