# Local-first operation and inbound cloud sync

The owner asked whether DaYo can remain local-first if it also pulls changes from the cloud. Sync direction does not decide this. Local-first principles support offline work and collaboration across devices. For DaYo’s restaurant deployment, the practical criterion is whether core on-site work can read and save data through the local app and Supabase stack during an internet outage, then reconcile changes when connectivity returns. A local server shared over the restaurant LAN still needs to be reachable by its terminals. [Local-first software paper](https://www.inkandswitch.com/essay/local-first/) · [Local Docker setup](../../../docker/docker-compose.yml) · [Manual POS service](../../../src/services/orderService.js#L49) · [Sync runbook](../../../sync/README.md#install-or-upgrade)

Cloud QR orders can flow into the local KDS when connected while POS and inventory use the local database. Future inbound menu edits would require an explicit conflict policy so cloud writes cannot silently undo pending local edits. In the current worktree the inbound path is limited to active orders and their lines. This architectural assessment does not verify a full live offline test or per-device offline storage.
