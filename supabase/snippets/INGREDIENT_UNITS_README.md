Ingredient entry uses exactly **Pcs**, **Grams**, and **mL**, saved with that spelling in `ingredients.unit`. Add and Edit share a required dropdown and service-side validation. Existing equivalent names (`pcs`, `g`, `grams`, `ml`, etc.) display consistently without changing quantities. Fractional stock and recipes retain the existing precision of 0.001.

Apply `supabase/migrations/20261030000002_ingredient_units.sql` after the ingredient unit-cost and reorder-point migrations. It converts existing kg to Grams and L to mL, multiplying stock, recipe quantities, all stock movements and saved thresholds by 1,000, and dividing per-unit cost by 1,000. ADS and ROP are recalculated from the converted ledger. Cost precision is expanded so conversion does not lose small per-gram costs. Records, order links, timestamps, and archive snapshots are retained. Historical archive snapshots keep their original units.

The conversion runs in one transaction and can be repeated without scaling quantities twice. Unknown custom units such as packs stop setup with their ingredient IDs; their sizes must be established before conversion. The script never assumes a pack size or a mass-to-volume conversion. A normal Edit cannot relabel stock or history into a different dimension; an unused ingredient with zero stock, threshold, and cost can change units.

The configured seed file also uses the canonical units. Seeded Rice stock, recipes, thresholds, and movements are expressed in Grams, so database resets remain compatible with the unit constraint.

For local/cloud synchronization, let pending changes finish and pause the sync worker while applying this setup on both databases, then resume it. Current application reads and stock notifications use the saved ingredient unit. Stock deductions and menu availability use recipe quantities in that same unit; valuation and ingredient revenue reports use cost per that unit. Sumo AI continues to use those availability results and expiry signals without exposing stock quantities to customers.
